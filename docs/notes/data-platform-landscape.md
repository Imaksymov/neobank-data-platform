# Ландшафт платформ данных: термины, различия, технологии

OLTP, OLAP, DWH, data lake, lakehouse, OLAP-кубы, векторные базы —
что это, откуда взялось, чем отличается и где встретится в проекте.

Правило чтения: почти все эти слова обозначают не технологии, а
**форму нагрузки**. Технологии появились как ответ на форму, и
путаница начинается там, где название продукта принимают за категорию.

---

## 1. OLTP и OLAP — две формы нагрузки

Это исходное различение, из которого выросло всё остальное.

| | OLTP | OLAP |
|---|---|---|
| Расшифровка | Online Transaction Processing | Online Analytical Processing |
| Типичный запрос | «баланс счёта 1787» | «оборот по месяцам за 6 лет» |
| Строк затронуто | единицы | миллионы |
| Колонок затронуто | все | 2–5 из 50 |
| Запросов в секунду | тысячи | единицы |
| Что критично | задержка отдельного запроса | пропускная способность |
| Запись | много мелких, постоянно | пакетами, редко |
| Нормализация | высокая (3NF) | низкая (звезда, плоские таблицы) |
| Хранение | **построчное** | **поколоночное** |

### Измерено на нашей базе

Один и тот же `berka.trans` (1 056 320 строк, 84 МБ), два запроса:

```
OLTP-форма:  select * from trans where trans_id = 695247
             Index Scan, 4 буфера (32 КБ), 3.8 мс

OLAP-форма:  select date_trunc('month', date), sum(amount)
             from trans group by 1
             Seq Scan, 10 824 буфера (≈84 МБ), 608 мс, результат — 73 строки
```

А теперь главное число: агрегату нужны были только `date` и `amount` —
это **10 МБ из 84, то есть 11.9%**. Остальные 88% ввода-вывода — колонки,
в которые запрос не смотрел.

Postgres не мог поступить иначе: он хранит строку целиком в одной
странице на 8 КБ. Чтобы прочитать два поля, он читает всю строку.

### Отсюда и колоночное хранение

Колоночный движок хранит все значения одной колонки подряд. Следствия:

1. **Читается только нужное.** Запрос выше прочитал бы ~10 МБ вместо 84.
2. **Сжатие работает в разы лучше.** В колонке однотипные и похожие
   значения: `date` имеет около 2200 различных значений на миллион
   строк — словарное кодирование сожмёт её в несколько раз; `type`
   с тремя значениями сожмётся почти в ничто. В строковом хранилище
   рядом лежат int, numeric и text — сжимать нечего.
3. **Векторизованное исполнение.** Операции применяются к блокам
   значений одного типа, а не к строкам по одной. Процессор работает
   с плотными массивами, попадая в кеш и используя SIMD.
4. **Позднее материализование.** Можно отфильтровать по одной колонке,
   получить список позиций и только потом поднять остальные поля.

**Обратная сторона.** Чтобы собрать одну строку целиком, колоночному
движку надо обратиться к N колонкам в N разных местах. Точечное чтение
и обновление отдельной строки — дорого. Поэтому `update` одной записи
в колоночном хранилище обычно не поддерживается вовсе или реализован
как «переписать блок».

**Вывод, который важен практически:** один движок не может быть хорош в
обоих режимах, потому что требования к раскладке данных противоположны.
Это не недоработка вендоров, а физика.

### HTAP — попытки середины

Hybrid Transactional/Analytical Processing: системы, обещающие оба
режима. Подходы: два хранилища внутри одной системы с репликацией
между ними (TiDB, SingleStore), либо колоночный индекс поверх
строковой таблицы (SQL Server columnstore, `citus_columnar` для
Postgres).

Работает, но с оговорками: аналитика медленнее специализированного
движка, транзакции медленнее специализированного OLTP, а сложность
выше обоих. Применимо, когда объёмы умеренные и очень не хочется
второй системы.

## 2. DWH — хранилище данных

**Что это.** Централизованное, смоделированное, управляемое хранилище
для аналитики. Данные приводятся к единой модели **до** загрузки —
schema-on-write.

**Что делает его хранилищем, а не просто базой:**

- **Интеграция.** Данные из нескольких источников сведены к общим
  определениям. «Клиент» значит одно и то же, откуда бы он ни пришёл.
- **Историчность.** Хранится не текущее состояние, а история:
  измерения с версиями (SCD2), факты с датами.
- **Неизменяемость.** Загруженное не правят, а дополняют. Отчёт за
  прошлый квартал должен воспроизводиться.
- **Ориентация на предмет, а не на процесс.** Таблицы организованы
  вокруг «кредиты», «транзакции», а не вокруг экранов приложения.

**Две школы моделирования** (ваш блок 2, недели 9–13):

- **Инмон** — нормализованное корпоративное хранилище (3NF), из него
  строятся витрины. Сверху вниз, дороже на старте, строже.
- **Кимбалл** — размерное моделирование (звезда: факты + измерения).
  Снизу вверх, от бизнес-процессов, быстрее даёт результат. Это то,
  что вы будете делать на неделе 10.
- **Data Vault** (неделя 11) — третий подход: хабы, линки, сателлиты.
  Оптимизирован под аудируемость и смену источников, поэтому любим
  в банках и под BCBS 239.

**Технологии:**

| Класс | Примеры | Особенность |
|---|---|---|
| Legacy MPP | Teradata, Exadata, Netezza, Greenplum | shared-nothing, своё железо, дорого |
| Облачные MPP | **Redshift** (неделя 33), Synapse | кластер, который вы масштабируете |
| Разделение хранения и вычислений | **Snowflake**, **BigQuery** | платите за хранение и за запросы отдельно, вычисления эластичны |
| Встраиваемые | **DuckDB** (неделя 8) | колоночный движок в процессе, без сервера |
| Специализированные на скорость | ClickHouse, Druid, Pinot | субсекундная аналитика, ограничения в JOIN |

**Главный архитектурный сдвиг последних лет** — разделение хранения и
вычислений. В Redshift классическом диск привязан к узлу: чтобы
хранить больше, добавляете вычислительные узлы, даже если вычисления
не нужны. В Snowflake и BigQuery хранение — в объектном хранилище,
вычисления поднимаются отдельно и под нагрузку. Отсюда же возможность
остановить вычисления и платить только за хранение.

## 3. Data Lake — озеро данных

**Что это.** Хранилище файлов в исходном или слабо обработанном виде,
обычно в объектном хранилище. Структура интерпретируется при чтении —
schema-on-read.

**Почему появилось.** Три причины, все практические:

1. **Объектное хранилище радикально дешевле** хранилища в составе DWH.
   Положить терабайт в S3 стоит единицы долларов в месяц.
2. **Не все данные табличные.** Логи, JSON от API, изображения,
   аудио — в DWH их грузить некуда.
3. **Вопросы ещё не заданы.** DWH требует решить модель заранее. Озеро
   позволяет сохранить всё и разобраться потом.

**Из чего состоит:**

- **Хранилище:** S3, GCS, Azure Blob, HDFS (исторически), **MinIO**
  (ваше, неделя 4)
- **Форматы:** **Parquet** (колоночный, доминирующий), ORC, Avro
  (строковый, для стримов), JSON/CSV (сырой приём)
- **Движки запросов:** Athena, Trino/Presto, Spark, DuckDB
- **Каталог:** Glue Catalog (неделя 33), Hive Metastore — отображение
  «таблица → набор файлов»

**Режим отказа: data swamp.** Озеро без дисциплины превращается в
болото. Конкретно чего не хватает:

- нет контроля схемы — продюсер поменял тип поля, и консьюмеры
  сломались молча;
- **нет транзакций** — читатель может увидеть половину записанного
  набора файлов;
- нет атомарной перезаписи — обновить партицию = удалить файлы и
  записать новые, и между этими действиями данные неконсистентны;
- нет истории версий и времени;
- нет происхождения и владельцев.

Именно этот список и закрывает следующий пункт.

## 4. Lakehouse — и что в нём реально нового

**Термин** придуман Databricks и наполовину маркетинговый. **Техническая
основа под ним — настоящая**, и называется она **табличный формат**.

**Идея.** Данные остаются файлами Parquet в объектном хранилище
(дешёвое, открытое). Сверху добавляется **слой метаданных**, который
описывает, какие именно файлы составляют таблицу в данный момент
времени. Коммит — это атомарная подмена указателя на новую версию
метаданных.

Из одного этого механизма следует всё остальное:

| Что получаем | Почему это работает |
|---|---|
| **ACID** | коммит = атомарная замена указателя, читатель видит либо старую версию целиком, либо новую |
| **Snapshot isolation** | читатель фиксирует версию метаданных и работает с ней, пока писатель создаёт следующую |
| **Time travel** | старые версии метаданных сохранены — можно запросить состояние на прошлую неделю |
| **Эволюция схемы** | схема хранится в метаданных, а не выводится из файлов; переименование колонки не требует перезаписи данных |
| **Эволюция партиционирования** | разбиение описано в метаданных, можно изменить без пересоздания таблицы |
| **Удаление строк без перезаписи** | файлы удалений (delete files) накладываются на данные при чтении |

**Три реализации:**

- **Apache Iceberg** (ваша неделя 38) — дерево метаданных:
  `metadata.json` → manifest list → manifest files → данные.
  Наиболее нейтрален к вендорам, поддержан почти всеми движками,
  де-факто становится стандартом.
- **Delta Lake** — журнал транзакций `_delta_log` из JSON-коммитов с
  периодическими чекпойнтами. Исторически завязан на Spark,
  сейчас открыт шире.
- **Apache Hudi** — акцент на upsert и инкрементальное чтение;
  copy-on-write против merge-on-read как режимы компромисса между
  скоростью записи и чтения.

**Честная оценка.** «Lakehouse» как архитектурный лозунг — «одно
хранилище для всего, и BI, и ML» — обещает больше, чем даёт: движки
всё равно разные, а производительность уступает специализированному
DWH на интерактивных запросах. **Но табличные форматы сами по себе —
одно из самых полезных изменений в инфраструктуре данных за десятилетие.**
Они дают озеру свойства базы, не отбирая у него дешёвое открытое
хранилище.

Ваш ADR на неделе 38 (`004-lakehouse-vs-dwh.md`) — ровно про этот
компромисс, и к тому моменту у вас будет опыт обоих.

## 5. OLAP-кубы — почему были и почему ушли

**Что это.** Многомерная структура, где метрики **предрассчитаны** по
всем комбинациям измерений. «Продажи по региону, товару и месяцу» уже
посчитаны и лежат готовыми — запрос не считает, а читает.

**Словарь, который из них пришёл** (и остался):
- **мера** (measure) — то, что агрегируется: сумма, количество
- **измерение** (dimension) — то, по чему разрезается: время, продукт
- **иерархия** — год → квартал → месяц → день
- **зерно** (grain) — уровень детализации факта
- **slice / dice / drill down / roll up** — операции над кубом

**Технологии:** Microsoft SSAS (multidimensional), Oracle Essbase,
SAP BW, Mondrian. Язык запросов — **MDX**, не SQL.

**Почему ушли.** Три причины:

1. **Комбинаторный взрыв.** Полный куб по 10 измерениям — это 2¹⁰
   групп агрегатов. Приходилось выбирать подмножество, то есть заранее
   решать, какие вопросы будут задавать. Новый разрез = перестроение.
2. **Колоночные движки стали достаточно быстрыми.** Если агрегат по
   миллиарду строк считается за секунду на лету, предрасчёт теряет
   смысл — а вместе с ним исчезают цикл перестроения и устаревание.
3. **Отдельная дисциплина.** Куб требовал своей модели, своего языка,
   своих специалистов. Обслуживать и его, и реляционное хранилище —
   двойная работа.

**Что пришло на замену — ROLAP и семантический слой.** Агрегаты
считаются по реляционным таблицам в момент запроса, а определения
метрик живут в декларативном слое:

- **dbt Semantic Layer / MetricFlow** — ваша неделя 20
- **Cube.dev**, **AtScale**, **LookML** (Looker)
- Табличная модель Power BI / SSAS Tabular (движок VertiPaq) — это, по
  сути, «куб, ставший колоночным»

**Что выжило целиком — концепции.** Звезда Кимбалла (неделя 10) — это
и есть куб в реляционной форме: таблица фактов = меры с зерном,
таблицы измерений = оси. Предрасчёт никуда не делся, но стал
**оптимизацией** (материализованные представления, агрегатные таблицы,
`pre_aggregations` в Cube), а не архитектурой.

## 6. Векторные базы

**Зачем они.** Эмбеддинг — представление текста, изображения или звука
числовым вектором (обычно 384–3072 измерения), где близость векторов
означает смысловую близость объектов. Запрос к такой базе — не «где
`x = y`», а **«найди k ближайших к этому вектору»** по косинусной
близости или евклидову расстоянию.

Реляционные индексы здесь бесполезны: B-дерево упорядочивает по одному
измерению, а близость в 1536-мерном пространстве к такому порядку не
сводится.

**Почему точный поиск не работает.** Перебор — O(n·d): миллион
векторов по 1536 измерений = полтора миллиарда операций на один
запрос. Отсюда **ANN — приближённый поиск ближайших соседей**:

| Тип индекса | Как работает | Характер |
|---|---|---|
| **HNSW** | многоуровневый граф «малого мира», спуск от грубого уровня к точному | лучшее качество/скорость, много памяти |
| **IVF** | кластеризация, поиск только в ближайших кластерах | компактнее, качество зависит от числа просматриваемых кластеров |
| **PQ** (product quantization) | сжатие векторов с потерями | экономит память в разы, теряет точность |

**Ключевое свойство, которого нет в SQL-индексах: приближённость.**
ANN-поиск **может не найти настоящего ближайшего соседа**. Вводится
метрика **recall** — доля истинных соседей среди найденных. И появляется
треугольник компромиссов: **recall ↔ задержка ↔ память**. Индекс можно
настроить на 99% recall и медленно, или 90% и быстро.

Для дата-инженера это непривычно: индекс, который иногда даёт неполный
ответ, и это нормальный режим работы, а не дефект.

**Технологии:**

| Класс | Примеры |
|---|---|
| Расширение существующей БД | **pgvector** (ваша неделя 47), `vss` в DuckDB, векторы в ClickHouse |
| Специализированные | Qdrant, Weaviate, Milvus, LanceDB |
| Managed | Pinecone, Vertex AI Vector Search |
| Поисковые движки с векторами | Elasticsearch, OpenSearch, Redis |

**Честная оценка.** Для большинства проектов **расширение
существующей базы выигрывает у отдельной системы**: меньше
компонентов, векторы можно соединять с реляционными данными одним
запросом (а это нужно почти всегда — фильтр по правам, по дате, по
клиенту), одна история бэкапов. Специализированные базы оправданы на
миллиардах векторов, при сложной многоарендности или когда нужны
специфические режимы фильтрации.

План выбрал `pgvector` на неделе 47 — и это правильный выбор для
вашего масштаба.

**И главное предупреждение оттуда же.** План формулирует так:
«качество text-to-SQL на 80% определяется качеством метаданных и на 20%
— моделью». Векторная база — это инфраструктура поиска по метаданным.
Если описания моделей и колонок пустые, никакой индекс не поможет.
Поэтому недели 12 и 15 (глоссарий, описания) — фундамент для недели 47,
а не бюрократия.

**Чем векторная база не является.** Она не замена OLTP или OLAP — это
третий тип доступа (поиск по сходству), живущий рядом с ними. В
нормальной архитектуре она дополняет реляционное хранилище, а не
конкурирует с ним.

## 8. Смежные термины, которые стоит знать

**ODS** (Operational Data Store) — слой, куда данные источников
копируются почти без изменений, для операционной отчётности и снятия
нагрузки с OLTP. Схема близка к источнику. Ваша схема `berka` играет
роль источника, а не ODS, но граница тонкая.

**Data mart** (витрина) — подмножество хранилища под конкретную
предметную область или группу потребителей. `fct_ecl_monthly` на
неделе 46 — витрина.

**Medallion architecture** (bronze / silver / gold) — терминология
Databricks для слоёв: сырое → очищенное → агрегированное. То же, что
`raw → staging → marts` в словаре dbt, который использует ваш проект.
Разные названия одной идеи; знать оба полезно, потому что в вакансиях
встречаются оба.

**ETL против ELT** — где происходит преобразование. ETL:
преобразовали по пути, загрузили готовое (эпоха, когда вычисления в
хранилище были дороги). ELT: загрузили сырое, преобразовали внутри
хранилища его же мощностями (современный подход, на нём построен dbt).
Ваш `load.sh` — это EL, а T начнётся на неделе 14.

**MPP** (Massively Parallel Processing) — архитектура shared-nothing:
данные распределены по узлам, каждый обрабатывает свою часть.
Отсюда ключевое решение в Redshift — **distribution style** (неделя 33):
как разложить таблицу по узлам, чтобы join выполнялся локально, а не
через передачу данных по сети.

**Semantic layer** — слой определений метрик между хранилищем и
потребителями. Решает проблему «у нас четыре разных числа активных
клиентов, потому что каждый считает по-своему».

**Data mesh / data fabric** — организационные концепции (владение
данными по доменам, самообслуживание). Технического содержания мало,
в вакансиях встречаются часто. Знать определение полезно,
строить по ним — обычно нет.
